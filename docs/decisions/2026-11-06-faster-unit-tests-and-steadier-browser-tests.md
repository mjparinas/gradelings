# Faster unit tests and steadier browser tests

**Faster unit tests and steadier browser tests** (November 6, 2026): the grade fairness tests spent about 93% of their time in vitest's `expect` (28.8 s of 31 s for Grade 4; generating the questions took 2.2 s), because every question is checked with dozens of assertions. `src/content/fairness/question.ts` now uses a small local `expect` with the matchers it needs and the same messages, so Grade 4 takes about 4 s; `question.test.ts` checks that it still fails bad questions. Coverage is unchanged (same 120 runs per unit). The curriculum lock test also reads each source file once. Shared workers were tried earlier and saved almost nothing.

Browser job flakes had separate causes, fixed at each one rather than by retrying: `e2e-keyboard.mjs` could not answer the newer question kinds (match, select-all, highlight, find the mistake, fill, tiles), so an Adventure that drew one waited out its 150 s limit (now handled; a used tile is disabled and an earlier pick must not be pressed again). The classroom script gave a student 200 tries instead of a time limit, and the admin script checked the overview with an instant visibility test, so a slow machine failed both. Both now wait on the clock. When a new question kind is added, add it to `playByKeys` in `scripts/e2e-keyboard.mjs` and to `stepOnce` in `scripts/helpers.mjs` in the same change.
