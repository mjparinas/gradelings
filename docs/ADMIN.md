# Admin panel

`/admin/` is the site-wide admin panel: headline numbers, a to-do list, users, emails to families, the inbox, redeem codes, feature flags, A/B tests, question reports and a change log. It is `noindex` and disallowed in `robots.ts`.

## Who can use it

An admin is an ordinary account whose **confirmed** email is listed in `ADMIN_EMAILS` (comma-separated, case doesn't matter):

```bash
ADMIN_EMAILS=owner@example.com
```

1. Sign up at `/play/` or `/teachers/` with that email and confirm it from the email link.
2. Open `/admin/` and sign in. Only a sign-in made after the email was confirmed counts: if you were already signed in from signing up, sign out and back in once. This stops someone who signed up first with an admin's address from becoming admin when its owner clicks the confirmation link.

The list lives in the environment, never the database, so nothing a request writes can make someone an admin. Without `ADMIN_EMAILS` the panel and every `/api/admin/*` route answer 404 (except `/api/admin/codes/`, which still accepts `ADMIN_TOKEN` for scripts, see `docs/CODES.md`). Every change made in the panel is written to `admin_audit` with the admin's email and shown under **Log**.

**Support role.** List an address in `SUPPORT_EMAILS` (comma-separated, same sign-in rules and two-step as an admin; an address on both lists is an admin) for a person who answers families but must not refund, delete or mass-email. Support staff see only the **Users** tab: search, a family's page (plan, children's grades, emails sent, **What This Family Sees**) and **Private Notes** (up to 1,000 characters; never shown to the family, no children's details; support removes their own, admins any). Every other admin route answers 404 and every other user action 403. Each family page a support account opens is written to the log as `user.view`; notes log only that one was added. Support accounts can't use Google sign-in, and notes are deleted with the family.

## Two-step sign-in

The panel can refund payments, delete families and email everyone, so a password isn't enough. Admin accounts must set up an **authenticator app** (Google Authenticator, Microsoft Authenticator, 1Password, Authy; any app that does time-based codes). Code is in `src/server/totp.ts` and `src/server/twoFactor.ts`.

- **Setting it up:** sign in at `/admin/` with the password as before. Until it is on, the panel shows only the setup screen: scan the QR code (or type the key), enter the 6-digit code it shows, and save the **eight recovery codes**, which are shown once. Turning it on signs the account out of every other device.
- **Signing in:** the admin sign-in asks for the code after a right password. A code works once (a code seen over a shoulder can't be reused), and it may be one step either side of the clock. Wrong codes are limited per account (8 in 10 minutes), so guessing from many places is limited too. A password alone opens nothing, even from a session made some other way, such as after a password reset by email.
- **Lost phone:** sign in with one of the recovery codes (each works once). Then open **System > Two-Step Sign-In**, make new recovery codes, or turn it off and set it up again on the new phone. Keep the recovery codes apart from the password, for instance in a password manager.
- **Lost phone and recovery codes:** someone with access to the database runs `node scripts/admin-2fa-reset.mjs owner@example.com` (it reads `DATABASE_URL`/`DATABASE_AUTH_TOKEN`, or `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`, like the app). That clears the account's two-step sign-in and signs it out; the admin then signs in with the password and sets it up again. It deliberately has no button in the panel, so a stolen admin session can't switch off someone else's protection.
- **Settings:** `ADMIN_2FA=optional` is for test servers only (the default is required). `TWO_FACTOR_KEY` encrypts the secrets in the database; set it before anyone turns two-step on. The System tab's settings list shows whether it is set.
- Setting it up, making recovery codes and turning it off are written to the **Log** (`2fa.enable`, `2fa.backup-codes`, `2fa.disable`). Turning it off needs the password and a code.
- Other accounts (parents, teachers) never see this; only an account that has it on is asked for a code, and only admin accounts can turn it on.

## Sections

Each tab has its own address (`/admin/?tab=Funnel`; a family's page is `/admin/?family=<id>`), and every tab you open, including one opened from a link inside another tab, is added to the browser history, so Back and Forward move between tabs and a reload or a shared link opens the same tab.

- **Overview:** a business dashboard with charts and a table view for each (`src/components/admin/Dashboard.tsx`, numbers worked out in `src/lib/adminMetrics.ts`). Class student accounts are left out; days and months are UTC.
  - **Revenue and profit:** monthly recurring revenue (list prices, yearly plans as a twelfth a month, counting only plans that renew: a plan cancelled to end at its period's end, or whose latest payment was refunded in full, stops counting the day it is cancelled, though it keeps access and still shows as paying, "cancelling") and the yearly run rate, revenue this month, last month and this year, profit this month and this year, projected revenue and profit for the year (revenue so far plus MRR for the months left), revenue per paying family, cancellations in 30 days (counted on the day the parent cancelled, from Stripe's `canceled_at` in `families.cancelled_at`, including plans still running until they end) with churn and an estimated lifetime value, a **Customer lifetime value** tile (a customer is a family with a payment not refunded in full; value is what they have paid so far, after refunds, CAD and USD apart; it opens a list, highest first, whose rows open the family), and charts of revenue, profit and paying families by month.
  - Revenue comes from the `payments` table: the Stripe webhook records `invoice.paid` (only invoices for families here) and `charge.refunded`, so add those two events to the webhook in Stripe. **Import Payments From Stripe** copies older paid invoices (needs `STRIPE_SECRET_KEY`). When a family deletes its account its payments stay in the totals with the family link cleared. All money is in CAD; US families' USD payments and MRR are never added in (nothing is converted) and show on their own tile once there are any.
  - Stripe fees are estimated at 2.9% + 30¢ a payment. Profit takes off those fees and the **monthly running costs** you enter on the dashboard (stored in `admin_settings`, changes go in the log).
  - **Customers:** families and parent or teacher accounts, paying (monthly, yearly, past due), in trial, free after the trial, code or admin access (lifetime), children per family, teachers, classes and student accounts, codes redeemed and question reports.
  - **Growth:** sign-ups this month, in the last 30 days against the 30 before, per week and per month; trial to paid (trials that ended in the last 90 days whose family pays now), paying share, activation (new families in the last 90 days who practised), confirmed emails and referrals. **Why Families Cancel** charts the reason a parent picked in Stripe's billing portal over the last 12 months (`cancellations` table, filled by the subscription webhook). Only the reason is kept; the optional comment is free text that could name a child, so it stays in Stripe.
  - **Practice:** families practising today, this week and this month, stickiness (daily ÷ monthly), questions answered and minutes per day for 30 days, and **Guest Players**: devices where a child played with no parent account, in the last 30 UTC days, 7 days and today (`guest_devices`, `src/server/guests.ts`). A guest's practice never leaves the device, so once a day the kids' app on a device with no account sends its random device id to `POST /api/guests/seen/` (only after a child answered a question that day, and never from an automated browser or for a US child or a signed-in or class student session; `src/lib/guestPing.ts`). The server keeps a one-way hash of the id and the last day it played, nothing else, deletes rows after 35 days in the daily job, and forgets a device when it signs in to an account (the next `/api/flags/` request with a session). Counting started the day this shipped, so earlier guests are not in it. The tile and its list use the same `guestCounts` query.
  - **Growth** also has **Try It Free Clicks** (last 28 days, from Vercel Web Analytics like the Traffic tab; `clickTotals` in `visitsReport`, cached 10 minutes). It counts clicks on "Try it free" and "Play free" links on public pages, not players, and its list (`clicksDetail`) shows them by page, with the pages Vercel folds into "Others" as one row so the list adds up to the tile. It shows "needs Vercel Analytics" when Vercel isn't set up and nothing when Vercel won't give custom events (they need a paid plan).
  - **Tile details:** most tiles open a window with the list behind the number (`GET /api/admin/stats/detail/?view=…`, `src/server/adminDetail.ts`; views in `src/lib/adminDetail.ts`): paying families with renewal dates, payments this month or this year with refunds and estimated fees, cancellations in 90 days, all families with their group, trials (soonest to end first), free families, code access with the codes used, codes redeemed, guest players by the day they last played, Try it free clicks by page, sign-ups (families and a 60-day count by day), trial outcomes, activation, unconfirmed emails, referrals, families who have paid, families practising, open classes with their teacher, and children counted by grade and province. The profit and projection tiles open a month-by-month breakdown. Lists show account emails (an email opens the family in Users) and stop at 200 rows. Children are only ever counts: never names or results.
- **To Do** (`src/server/adminQueue.ts`, `GET/POST /api/admin/queue/`): families worth acting on now, worked out fresh each time, each with the action that fits, plus owner setup tasks kept in code. The tab shows how many items wait.
  - **Set up the social accounts:** create the Instagram, YouTube, Pinterest and Facebook accounts (`SOCIAL_PLATFORMS` in `src/lib/brand.ts`) and add each profile's URL to `SOCIAL_PROFILES`. The item names the platforms still missing and goes away once each is listed. YouTube is put off for now (`later`), so it isn't asked for.
  - Mail in the inbox nobody has answered or set aside (last 14 days): **Read and Reply**.
  - Payment failed (`past_due`): **Open Family**.
  - Trial ends within 3 days, a child has practised, not paying: **Write Email** with the trial-ending message.
  - Cancelled in the last 14 days: a "what didn't work?" email.
  - Paying but no practice for 14 days: the "Ollie misses you" email.
  - Signed up 2 to 14 days ago, never practised: a getting-started email.
  - Email not confirmed after a day (and no confirmation sent in 2 days): **Resend Confirmation**.
  - Email bouncing (30 days) and waiting question reports.
  - A family emailed from the panel drops off for 7 days. **Snooze a Week** or **Dismiss** hides an item (`admin_queue_hidden`); an item also goes away on its own once the family moves on.
- **Users:** search by email or family id (class student accounts are left out). The list shows each account's last sign-in (`parents.last_login_at`, set at every sign-in) and last practice. A family shows its plan, trial, lifetime value (payments after refunds), access, subscription, a waiting discount, last practice, devices signed in, codes used, A/B test groups and each child's grade and province. Children's names and results are never shown. Actions: extend the trial, add days of free access or give lifetime access, remove access, mark an email confirmed, sign out everywhere, force a feature flag on or off for the family, email the family (below) with the history of every email it was sent, and delete the account (type the account's email to confirm; it cancels any Stripe subscription first and deletes everything, the same as a parent deleting their own account; your own account can't be deleted here).
  - **Billing** (`src/components/admin/Billing.tsx`, `GET/POST /api/admin/billing/`, `src/server/adminBilling.ts`): the family's payments and its live Stripe subscription, read from Stripe each time. **Refund** a payment in full or in part (type `REFUND`; never more than is left), **Cancel at the End of the Period** or **Undo the Cancellation**, and **Cancel Now** (type `CANCEL`; no refund for the rest of the period, so refund a payment as well if you want to). Refunds and cancellations go through Stripe, and the webhook then updates the family and the revenue numbers as usual. When the last payment failed, **Email Them to Update Their Card** sends a short billing notice with a link to Subscription (Stripe's Billing Portal). It's a billing notice, so it goes even with news and tips off, but never to an address that bounced. Every action is in the change log (`billing.*`). Needs `STRIPE_SECRET_KEY`.
  - **Download accounts CSV** and **Download payments CSV** (`GET /api/admin/export/?type=users|payments|emails`): one row per family (email, sign-up, plan, trial, access, last sign-in and practice, number of children, total paid, news and tips) or per payment. No child's name or results are in any file. A cell that starts with `=`, `+`, `-` or `@` gets a leading apostrophe so a spreadsheet never runs it as a formula. Each download is in the change log.
- **Funnel** (`src/components/admin/Funnel.tsx`, `GET /api/admin/funnel/?days=30|90|365`, `src/server/adminFunnel.ts`): of the families who signed up in the period, how many confirmed their email, added a child, had a child practise, practised on 3 or more days, and paid. It names the step that loses the biggest share, and each step past confirming has a link that opens **Emails** on the group stuck there (No child added, Never practised, Tried it then stopped, Practising often but not paying). Those groups cover every family at that point, not only the period's sign-ups. Class student accounts are left out.
- **Traffic** (`src/components/admin/Traffic.tsx`, `GET /api/admin/traffic/?days=7|28|90`, `src/server/traffic.ts`, cached 10 minutes; **Check Again** skips the cache): two parts, each read on the server so no credential reaches the browser, and each showing **Not set up** with the settings to add until they're set.
  - **Google Search** (Search Console): clicks, times shown, click rate and average position against the period before, clicks and impressions by day, the top searches and top pages, and the sitemaps with when Google last read them and any errors. Google's numbers settle late, so the period ends three days ago. Setup: in Google Cloud, create a service account (no roles needed) and a JSON key for it; in Search Console, add the service account's email to the property as a **Restricted** user (read-only). Set `GOOGLE_SERVICE_ACCOUNT_KEY` to the JSON key (as is, or base64) and `SEARCH_CONSOLE_SITE` to the property (`sc-domain:example.com` for a domain property, or the URL prefix such as `https://www.example.com/`). The app signs in with the read-only scope `webmasters.readonly` only.
  - **Visits to the Public Pages** (Vercel Web Analytics): visitors and page views against the period before, visitors by day, top pages, the sites that sent visitors, and countries. On a Hobby plan Vercel keeps only the last 31 days, so a longer period shows those days and no comparison. It uses the System page's `VERCEL_TOKEN`, `VERCEL_PROJECT_ID` and `VERCEL_TEAM_ID`. Vercel Web Analytics sets no cookies and is off in the kids' app, the parent area and account pages (`SiteAnalytics.tsx`), so nothing a child does is counted. Google Analytics isn't used (chosen by the owner, October 2026).
- **Emails** (`src/components/admin/Engage.tsx`, `/api/admin/email/`): the 30-day sent, delivered, bounce and spam counts, the email log (with **Download CSV**), and **Email a Group**.
  - **The email log** (`email_log`, `src/server/emailLog.ts`): every email to an account, with its kind (confirmation, reset, weekly report, trial notices, reminders, panel emails, replies), when, who sent it from the panel, and its status. It keeps the kind, the subject as written and the status, never the body, so children's names (which some emails carry) aren't stored. Mail to an address with no account isn't logged.
  - **Delivery reports:** add a Resend webhook pointing at `/api/email/webhook/` for `email.delivered`, `email.delivery_delayed`, `email.bounced` and `email.complained`, and set `RESEND_WEBHOOK_SECRET` to its signing secret (`whsec_…`). The route checks the Svix signature and answers 404 without the secret. A status never moves back (delivered stays delivered after a late "delayed"). A bounce or spam complaint marks the address (`parents.email_bounced_at`) so the panel stops emailing it; a complaint also turns off news and tips.
  - **Writing an email** (one family, from Users or the to-do list, or a group): pick a message (Ollie misses you, Getting started, Trial ending, Come back, What didn't work?, or your own; `MESSAGE_PRESETS` in `src/lib/adminEmails.ts`), edit the subject and text, and add a button to a page of the site. `{children}` becomes the children's first names and `{app}` the app's name, filled in only when it's sent; the panel's preview shows a stand-in, so names never reach the panel. Every panel email carries an unsubscribe link (`kind=updates`) and the mailing address (CASL).
  - **Who gets panel email:** the family's first account, only if its email is confirmed, it hasn't turned off **News and tips** (Parent area > Account & sync, `parents.admin_mail`, on by default; the unsubscribe link turns it off) and its address hasn't bounced. An unconfirmed account can only be sent the real confirmation email again.
  - **Email a Group** (`SEGMENTS`): gone quiet (practised before, not in 7 days), never practised, no child added (signed up 2 to 60 days ago), tried it then stopped (practised on 1 or 2 days, nothing for 3 days, not paying), practising often but not paying (3 or more days), trial ending in 7 days, trial over and not paying, cancelled in 90 days, or everyone. The panel shows how many it reaches and who is left out (unconfirmed, unsubscribed, bouncing, emailed from the panel in the last 3 days), and sends only after you type `SEND n` back. It sends at most 100 at a time, about two a second; sending again continues with the rest, because anyone just emailed is skipped. A failed send doesn't count, so the family can be tried again. Every group send is in the change log.
- **Inbox** (`src/server/inbox.ts`, `/api/admin/inbox/`): mail Resend receives for your domain, read live from Resend's receiving API, so bodies are never copied into the database. Messages show as the sender formatted them, with the sender's account when the address matches one: the HTML is sanitized on the server against an allowlist (`src/server/emailHtml.ts`: no scripts, event handlers, forms, frames or links but http(s) and mailto; links open in a new tab) and shown from `/api/admin/inbox/view/` in a sandboxed frame with no scripts or same-origin access, under its own strict Content-Security-Policy. Images from the internet stay blocked (they tell the sender the mail was opened) until you press **Load Images**. **Show Plain Text** switches to the text version, and mail with no HTML part shows as text. **Send Reply** answers in the same thread (`In-Reply-To`); **Mark as Done** sets it aside (`inbox_state`). **Archive** (on each row and on an open message) moves it out of the list to **Archived**, where **Move to Inbox** brings it back; the mail stays in Resend. The Inbox tab shows how many of the newest 50 messages are still waiting (not answered, marked done or archived; `?count=1`). **Draft With AI** (shown when `ANTHROPIC_API_KEY` is set; `src/server/replyDraft.ts`) asks Claude for a first draft from the help page answers and your saved replies, and puts it in the reply box; nothing is sent until you press **Send Reply**, and the draft isn't stored. Each draft sends that one message to Anthropic (disclosed on `/privacy/`) and is written to the change log as `inbox.draft`. Needs receiving set up in Resend and an API key with full access (a sending-only key can't read received mail).
  - **Saved Replies** (`src/lib/savedReplies.ts`, `GET/PUT /api/admin/replies/`): answers to common questions (billing and cancelling, adding a child, deleting an account, thanks) that **Insert a saved reply** adds to the reply box, to change before sending. **Edit** changes, adds or removes them (up to 30); the list is kept in `admin_settings` and every save is in the change log. `{app}` becomes the app's name.
- **Automations** (`src/components/admin/Automations.tsx`, `GET/POST /api/admin/automations/`): the alerts and morning digest switches, and the automatic nudges. See below.
- **Codes:** make free-access codes (days or lifetime) and discount codes (percent off the first payment, a number of months or every payment), with an optional use limit, expiry date, custom code and note; see each code's uses and disable one. Built on `/api/admin/codes/` (`docs/CODES.md`).
- **Sales:** site-wide sales. Pick a preset (Founding families, Back to school, Report card season, Black Friday through Cyber Monday, Christmas, New Year, Spring break, Summer learning, or Custom), change the headline and message, link an existing working code, pick where the button goes (pricing, Subscribe or the free trial) and the dates. `{percent}`, `{code}` and `{for}` are filled in from the code. While a sale runs, a banner with the code and a countdown sits above the header on every public page and on the parent area's Subscription page; seeing it remembers the code on that device, so the parent area's "Have a code?" box is filled in. Of overlapping sales, the one that started last shows. The banner disappears if its code is disabled, expires or is used up, and never shows in the store apps. Stop now ends a sale at once; the public feed (`/api/promo/`) is cached for a minute. Code: `src/lib/promo.ts`, `src/server/promo.ts`, `src/components/admin/Sales.tsx`, `src/components/site/PromoBanner.tsx`.
- **Flags:** switch a feature off for everyone or roll it out to a percentage of families. See below.
- **A/B Tests:** see below.
- **Feedback:** what parents and teachers send from the "How's Gradelings?" card (a parent's Overview after a good week) and the "Send feedback" button at the foot of the parent and teacher areas: a 1 to 5 face, an optional line and topic. Nothing is about a child. The sender's email shows only when they ticked "OK to email me back" and were signed in. A low rating (2 or less) or any written comment goes on the To Do list until you mark it done. The flag `app-feedback` turns the card, the button and the endpoint off. Feedback is deleted with the account.
- **Reports:** "Report a problem" submissions grouped by question, most reported first, with the curricula it was reported in and what was on screen in the latest report (the picture, the choices with the right answer marked). The report email lists the same, without the picture. Clear a question once it's fixed or checked.
- **System** starts with the **Maintenance Mode** switch (below), then the health checks (`src/server/systemHealth.ts`, `GET /api/admin/system/`, `?refresh=1` to skip the one-minute cache): one card per part of the stack, then the providers' status pages. Every token stays on the server; the page only gets results, and the Settings card shows a setting's name, never its value. A check that isn't set up shows **Not set up** with the settings to add; a service that errors or takes over 8 seconds shows **Down** without holding up the rest. The **Auto refresh** switch (off by default, remembered per browser) looks again every 5 minutes (`AUTO_REFRESH_MS` in `System.tsx`) while the tab is in view, without `?refresh=1`, so the server's one-minute cache and the six-hour Stripe checkout test still apply; a hidden tab asks for nothing and catches up when it comes back.
  - **Database:** answer time of `SELECT 1`, families, practice events and when practice was last saved.
  - **Uptime:** the `uptime.yml` workflow's pings over 24 hours and 7 days, the last failure, and how long the site has been down while its "uptime" issue is open. Needs `GITHUB_TOKEN` and `GITHUB_REPOSITORY`.
  - **Deploys (Vercel):** what's live in production, a failed latest production deploy, failed deploys in 7 days, deploys in 24 hours against the plan's daily limit (read from Vercel: Hobby 100, Pro 6,000, Enterprise none; Pro if Vercel doesn't say), and the commit this server runs. Needs `VERCEL_TOKEN` and `VERCEL_PROJECT_ID` (plus `VERCEL_TEAM_ID` for a team project).
  - **Builds (GitHub Actions):** the latest CI runs on main, and any running now.
  - **Errors (Sentry):** unresolved issues seen in 14 days, with events, how long each has been open and when last seen. Needs `SENTRY_READ_TOKEN` (or a `SENTRY_AUTH_TOKEN` that can read issues), `SENTRY_ORG` and `SENTRY_PROJECT` (`SENTRY_API_BASE=https://de.sentry.io` for an EU organization).
  - **Payments (Stripe):** whether checkout works, checked without charging anyone: the key and its mode (a test key on the live site is down), whether the account can take payments, each configured price (CAD, and USD when set) exists for this key, is active and charges what the site shows, a **test checkout** per currency (a Checkout Session opened exactly as a family's would be, then expired at once so nobody can pay it; a pass is kept for 6 hours or until the key or a price id changes, so the 15-minute watch doesn't open one each time), Stripe Tax for US checkout, the webhook endpoint to this site and whether it sends every event the app needs, the billing portal, events Stripe couldn't deliver in 7 days, and the app's own webhook record (received, failed, and why). Stripe can't say whether `STRIPE_WEBHOOK_SECRET` matches the endpoint's signing secret; a mismatch shows as failed webhooks with "Bad signature".
  - **Email (Resend):** sending domains and whether they're verified, emails in 30 days with bounce and spam rates (warns at Resend's limits, 4% and 0.08%, from 20 emails), and the last delivery report.
  - **Daily email job:** each run of `/api/cron/weekly/` (`job_runs`, `src/server/monitor.ts`), what it sent, and a warning when it hasn't run for 26 hours or when a run ran out of time and left phases undone (the hourly `?resume=1` runs then carry on, `docs/DEPLOY.md`).
  - **Backups:** when a restore was last practised (`docs/RESTORE.md`), recorded with **Record Restore Practice** on the card (a date not in the future, in `admin_settings`, and in the change log as `restore-drill.record`). Warns when none is recorded or the last is over 35 days old (`RESTORE_DRILL_DAYS`). Turso makes the backups itself; this card tracks whether anyone has proved they can be restored. Not shown for a local database file.
  - **Speed (Sync):** `POST /api/sync/` over 24 hours from Sentry's events API (`SENTRY_READ_TOKEN` needs organization read access as well as Issue & Event): timed syncs, typical and slowest 1 in 20 (p50, p95) times, the share that failed, and the count of `fetch failed` errors (the server couldn't reach the database or another service). Only the share of syncs that Sentry samples are timed (`src/lib/sentry-traces.ts`). Warns at a p95 over 3 s, 5% failing or 5 `fetch failed` errors. If Sentry answers one of the two queries and not the other, the card says so and warns. Not tested against a live Sentry account yet: if a row says it couldn't read the timing, check the Sentry query in `speedCheck`.
  - **Admin security:** each address in `ADMIN_EMAILS` and `SUPPORT_EMAILS` with whether two-step sign-in is on, whether the server requires it (`ADMIN_2FA`), failed staff sign-ins in 24 hours and 7 days, and when the last "repeated failed admin sign-ins" and class sign-in guessing alerts went out. Failed sign-ins (wrong password, wrong code or too many tries) for a listed staff address are kept 30 days in `staff_sign_in_failures` (the address and which step failed, never for any other visitor). Five failures within 15 minutes email the admins once every 6 hours (`reportStaffFailure` in `src/server/alerts.ts`; the alerts switch under Automations turns it off).
  - **Capacity:** the database's size (page count times page size), practice events written (the highest event number, which is never reused), one size sample a day kept for 90 days to show growth and, once the sample history is over a week old, how long until the limit. Set `DATABASE_SIZE_LIMIT_MB` to the Turso plan's storage to get a warning at 70% and a "down" at 90%. Practice events are never deleted, so the database only grows.
  - **Settings:** every required and recommended setting is present, and `ALLOW_DEV_BILLING` isn't on in production.
  - **Provider status pages:** Vercel, GitHub, Sentry, Resend, Stripe and Turso, with open incidents and how long each has been open.
  - Webhook records (`webhook_log`) and job runs are kept 60 days and hold no personal data.
- **Log:** the last 200 changes made in the panel.

## Maintenance mode

`src/lib/maintenance.ts`, `src/server/maintenance.ts`, `src/proxy.ts`, `GET/PUT /api/admin/maintenance/`. Switched on the **System** tab (type `TURN ON`); switching it off needs no typing. Both are in the change log (`maintenance.on`, `maintenance.off`).

- **While it's on,** every page except the home page answers `503` with a short "under maintenance" page, and every API route answers `503` with `{ error }`. Every answer carries `x-maintenance: on`.
- **Still working:** the home page, the admin panel and its API, signing in and out (`/api/auth/login/`, `/logout/`, `/me/`), the Stripe and Resend webhooks, unsubscribe links, the scheduled jobs (`/api/cron/`), the uptime check (`/api/health/`) and static files.
- **Devices keep working offline:** the service worker treats a maintenance answer for `/play/` or `/parents/` like no connection and opens the saved copy. Sync waits, telling parents under Account that progress is saved on the device, and uploads when maintenance ends. A device that never saved the app sees the maintenance page.
- **Every admin tab shows a banner** while it's on, with **Turn Off Maintenance Mode**.
- **Timing:** each server re-reads the switch every 15 seconds, so it can take that long to reach every visitor. If the database can't be read, the site stays open.
- **Cost:** the proxy runs on every page request, not only on shared reports, so Vercel counts a proxy (middleware) call for each page view.

## Alerts and the morning digest

`src/server/alerts.ts`. Both go to every admin account (a confirmed email in `ADMIN_EMAILS`) and can be switched off under **Automations**.

- **Alerts** when something goes wrong: a payment fails (`invoice.payment_failed`) or is disputed (`charge.dispute.created`), with a link to the family; the daily job fails or throws; or a System check goes down, and again when it's working again. The same alert goes out at most once every 6 hours.
- **System watching:** `/api/cron/watch/` (needs `CRON_SECRET` as a bearer token) runs the System checks and alerts on any that changed. The **Uptime** workflow calls it every 15 minutes after a good ping once the GitHub repository secret `CRON_SECRET` is set to the same value as the site's. Without it, only the site-down issue is opened.
- **Morning digest:** sent with the daily job. The last 24 hours' sign-ups, payments, revenue and cancellations, what waits in **To Do**, and any System problems. Counts only, never children.

## Automatic nudges

`src/lib/automations.ts`, `src/server/automations.ts`. An email the daily job sends by itself to families who reach a point: **Ollie misses you** (gone quiet 7 days; families who get practice reminders are left out), **Add your child**, **Come back after a try** and **Free lessons are waiting** (trial over, not paying).

- **Every nudge is off** until an admin turns it on and types `TURN ON`. Who switched it on and when is shown and logged (`automation.on`, `automation.off`).
- Each has a **daily limit** (20 by default, at most 50) and an editable message with a preview. The card shows how many families are waiting and how many the next run would email.
- They follow the panel's email rules (confirmed, news and tips on, not bounced, not emailed from the panel in the last 3 days), and a family gets the same nudge at most once in 30 days. Sends show in the email log with `auto:<id>` as the sender.

## Feature flags

Flags are defined in code, in `FLAGS` in `src/lib/flags.ts`, so the panel can only switch things that exist. A row in `feature_flags` appears once an admin changes one; until then the flag's default applies.

| Flag | Where | What it switches |
| --- | --- | --- |
| `daily-challenge`, `speed-run`, `math-facts`, `arcade`, `sticker-book`, `my-room`, `shop` | Kids' app | The home-screen tile and its screen (an open screen falls back to the home screen) |
| `secrets` | Kids' app | The Konami code, secret words and the moose |
| `signups` | Server | Creating accounts (`/api/auth/signup/` answers 503 while off) |
| `redeem-codes` | Server | Redeeming codes |
| `new-classes` | Server | Creating classes (existing classes keep working) |

A flag is decided in this order (`flagOn`): a per-family override (Users), then off for everyone if switched off, then the rollout. A partial rollout uses a stable hash of the flag and the family id, so the same families keep it and raising the percentage only adds families. Signed-out devices are bucketed by a random device id (`grademap.device` in `localStorage`); class student sessions count as signed out.

The kids' app fetches `/api/flags/` when it opens, when it comes back into view and when the signed-in account changes, and keeps the last answer in `localStorage` (`grademap.flags`) so it still applies offline. Read a flag with `useFlag("key")` or `useIsOn()` from `src/lib/remoteFlags.ts`; on the server use `isFlagOn("key", familyId)` from `src/server/flags.ts`.

**Adding a flag:** add it to `FLAGS`, read it where the feature is shown (and on the server if the feature has an API), and add a test.

## A/B tests

An experiment has a key, a description and 2 to 5 variants with weights; the first variant is the control.

- **Draft:** everyone sees the control and nothing is counted. Variants can still change.
- **Running:** each family or device gets a variant from a stable hash of the key and its id. A signed-in family is recorded in `experiment_assignments` the first time its app asks, so results can be counted. Variants can't change any more, because families would move between groups.
- **Stopped:** everyone sees the winner you pick (or the control).

Results per variant: families counted, how many now pay, and how many practised in the last 7 days, each with a two-sided p-value against the control (two-proportion z-test, `pValue` in `src/lib/flags.ts`). Under 0.05 is unlikely to be chance; with small groups, wait for more families.

A running test also gets a plain verdict on paying families (`src/lib/abVerdict.ts`): too early until each variant has 30 families, then which variant is ahead and how likely it is to really beat the control. **Use {variant} for everyone** stops the test with that winner; the button is highlighted once it's at least 95% likely.

A test only changes something where code asks for it: `useVariant("key")` in the kids' app (null when the test doesn't exist, which means the control), or `variantsFor(familyId, null)` on the server. Ship that code first, then start the test.

## Unlimited coins for testing

A device signed in to an admin account (a confirmed email in `ADMIN_EMAILS`) gets `testCoins` from `/api/flags/`, and the kids' app then adds 1,000,000 coins to each child's balance (`TEST_COINS` in `src/lib/store.ts`), so you can try the Shop and My Room with your own children. Nothing is stored or synced: only the balance shown and spent changes, trophies still count coins really earned, and level and trophy locks on shop items still apply. It goes away when the device signs out of the admin account, and anything bought then leaves that child's real balance below zero until they earn it back. Nobody else ever gets it; children can still never buy anything with money.

## Privacy

The panel shows parents' account emails and billing state, never children's names, practice details or class student accounts. The email log keeps no bodies and the inbox isn't copied into the database. CSV downloads hold account and payment data only, and alerts and the digest carry counts and links, never children. The change log keeps no email for deleted accounts. Deleting an account removes its flag overrides, test assignments and email log along with everything else (`src/server/deleteFamily.ts`).
